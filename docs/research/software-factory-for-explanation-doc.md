**Purpose**: Phase 1 evidence base for the Diataxis _Explanation_ page `site/software-factory/explanation/sf-explanation.md`. Explanation answers "why", so this document emphasizes history, rationale, alternatives and limits rather than steps.

## Executive Summary

**Verdict.** The repo's "software factory" ("the set of coding agents, instructions, skills, and workflows that turn issues into tested, reviewed code") belongs to a long line of thought. Its constant idea is to **reduce variability and encode know-how in a configured environment, so skilled people spend time on judgment rather than rote work**. According to Cusumano's history (available to this research only at snippet/bibliographic level; Medium-Low confidence), Bemer at GE is credited with an early "software factory" proposal, around 1968, to reduce variability in programmer productivity through standardized tools and management data. Cusumano's 1991 study of Japanese software factories is likewise cited bibliographically only (process discipline, reuse, quality control). Microsoft's Software Factories (Greenfield & Short 2004) proposed moving "from documentation to automation" by packaging knowledge as reusable assets, explicitly _not_ turning developers into "drones". The agentic version (2025-26) keeps the goal but swaps the mechanism. Knowledge now lives in natural-language artifacts (AGENTS.md, skills, docs/agents/*) consumed by a **probabilistic** agent rather than in deterministic generators. That one change explains most of the design: because the worker is non-deterministic, verification (tests, typecheck, lint, CI, independent review) and a human delegation decision become the load-bearing parts. In this repo the delegation decision is *designed\* as the `ready-for-agent` / `ready-for-human` triage convention documented in `docs/agents/triage-labels.md`. It is a documented convention, not a running gate: whether the labels exist on GitHub was not verified (no authenticated `gh`), and no automation reads them.

**Rationale is supported, with varying strength.** (1) **High**: agents need an executable pass/fail check, or, in the Claude Code docs' words, "that makes you the test suite" (Claude Code docs, Anthropic, Morris on martinfowler.com, Willison). (2) **Medium-High**: instructions are probabilistic and only hooks/CI enforce (Claude Code docs; Beck on the genie "cheating ... by disabling or deleting tests"). (3) **High**: context is a finite resource, so instructions should be short, layered and loaded just in time (Anthropic context engineering, Agent Skills progressive disclosure, AGENTS.md nearest-file rule). (4) **Medium-High**: AI _amplifies_ the existing system and "improves throughput, but often at the cost of stability if your foundation isn't solid" (DORA year-in-review fetched; full 2025 report not read). Diataxis's own definition of Explanation (history, context, alternatives, opinion, closely bounded) fits this page.

**Honest state of the repo (local fact).** The factory is mostly _configuration and convention_, not yet _automation_. What exists: AGENTS.md, three docs/agents adapter files, a five-label triage vocabulary adopted from mattpocock/skills (documented only), an npm script `checks` that AGENTS.md calls "the pre-commit gate", and a Diataxis site skeleton. `checks` is an **agent-instructed gate, not an enforced hook**: there is no husky, `core.hooksPath`, lint-staged or Claude hook. It also **probably cannot pass yet**. `tsconfig.json` includes only `src/**/*` and `vitest.config.ts` only `src/**/*.{test,spec}.ts`, `src/` does not exist, and there are no test files. That is an inference from tool defaults, not executed. There is also **no source code, no checked-in skills (`.agents/skills/.gitkeep`), no CONTEXT.md, and no CI running tests/lint/typecheck**. The only CI is an actions-lockfile supply-chain check and the Pages build. Main risks the Explanation should name: deskilling (Anthropic RCT: 50% vs 67% quiz score), review becoming the bottleneck, the factory metaphor hiding design work, and the gap between instruction and enforcement.

## Findings

### Area 1: Lineage of the term "software factory"

_Area confidence: Medium-Low for the pre-2004 history (F1.1, F1.2: snippet/bibliographic support only); High for Microsoft 2004 (F1.3); Medium for recent usage (F1.4)._

#### F1.1 Bemer (GE, c. 1968) is credited in Cusumano's history with an early "software factory" proposal

**Evidence** (search-snippet text, not read in a fetched page): Cusumano's MIT working-paper material says that R. W. Bemer, a General Electric engineer, "made numerous suggestions that culminated in a 1968 paper encouraging GE to develop a 'software factory' to reduce variability in programmer productivity through standardized tools, a computer-based interface, and an historical database for financial and management control." It adds that GE's 1970 exit from the computer business ended the effort. (Revision 2: the "probably the earliest proponent" claim was dropped because its source, an unnamed review paper seen only as a snippet, is not traceable.)
**Source (bibliographic only, non-load-bearing)**: Cusumano, M. A., "Factory concepts and practices in software development: an historical overview", MIT Sloan School working paper, 1989 — DSpace record [dspace.mit.edu/handle/1721.1/47992](https://dspace.mit.edu/handle/1721.1/47992) (record fetched, no abstract; the PDF fetch returned HTTP 429). Snippet text was also indexed at core.ac.uk (not on the trusted list, not used as a source). Cusumano also published a 1989 _IEEE Software_ article on the same topic (6(2)); its title and DOI appeared only in a third-party index and are **unverified**, so this document cites only the MIT working paper.
**Confidence**: Medium-Low. One author, snippets only, no trusted-list host fetched. (Revision 2: an untraceable Computer History Museum snippet was removed.) **Use in the Explanation**: hedged ("is usually credited", "according to Cusumano's history"), and not as a load-bearing premise.
**Do not claim**: that Bemer presented the term at the 1968 NATO Garmisch conference. No source in this document supports that link. See Conflicts C1.
**Analysis**: From its first use, "factory" meant _reducing variability_ through standardized tools plus measurement/feedback data, not mechanizing creativity. That framing carries over directly to an agent factory, where the variability is now in agent output.

#### F1.2 Japanese software factories (Cusumano 1991): organization, process discipline, reuse, quality control

**Evidence**: Cusumano, _Japan's Software Factories: A Challenge to U.S. Management_ (Oxford University Press, New York, 1991; 513 pp.; ISBN 0-19-506216-7). Catalog and review records describe case studies of System Development Corporation (a U.S. "factory experiment"), Hitachi (process and quality control), Toshiba, NEC and Fujitsu, and the theme of large teams developing software cooperatively under factory-style management.
**Source**: [Oxford Academic record](https://academic.oup.com/book/52424); [Cambridge, Business History Review review](https://www.cambridge.org/core/journals/business-history-review/article/abs/japans-software-factories-a-challenge-to-us-management-bymichael-a-cusumano-new-york-oxford-university-press-1991-ix-513-pp-charts-tables-appendixes-notes-and-index-3500-isbn-0195062167/9660A7E9024841575ACCEF610B132A03); [Cambridge, Journal of Asian Studies review](https://cambridge.org/core/journals/journal-of-asian-studies/article/abs/japans-software-factories-a-challenge-to-us-management-by-michael-a-cusumano-new-york-oxford-university-press-1991-513-pp-3500/FCF25AF1A70A9B7C5D7C0FE36E9FDF84) — all via search-result metadata; book text not accessed. These hosts (OUP, Cambridge) are reputable academic publishers but **not on the provided trusted list**. They are scored 0.6 and used **bibliographically only (non-load-bearing)**.
**Confidence**: Medium-Low. Existence, author, publisher and year are reliable. The characterization of contents comes from catalog/review abstracts, not the book. **Use in the Explanation**: cite the book as the classic study; do not attribute specific findings to it without reading it.
**Analysis**: The Japanese factories were an _organizational_ innovation (standard process, tools, reuse libraries, training, quality metrics) applied to large, repeated project types. The agent factory in this repo borrows the "standard process + tooling + quality control" idea, at a tiny scale, with agents rather than large staffs.

#### F1.3 Microsoft Software Factories (Greenfield & Short, 2004): product lines, models, frameworks, tools; economies of scope, not scale

**Evidence** (fetched, primary): "A Software Factory is a development environment configured to support the rapid development of a specific type of application." It promises "to change the character of the software industry by introducing patterns of industrialization." The recurring pattern: identify reusable abstractions, document patterns, codify them in a framework, then "define a language and build tools ... to automate the assembly process." On the metaphor: "software development will never be reduced to a purely mechanical process tended by drones. On the contrary, the key ... is to stop wasting the time of skilled developers on rote and menial tasks." And: "give developers ways to encapsulate their knowledge as reusable assets that others can apply ... The next step is to move from documentation to automation." Development should seek "economies of scope", not scale: "It makes no sense to look for economies of scale in development of any kind."
**Source**: [Greenfield, J. "The Case for Software Factories", Microsoft Architecture Journal, July 2004 (Microsoft Learn archive)](<https://learn.microsoft.com/en-us/previous-versions/aa480032(v=msdn.10)>). Book: Greenfield & Short, _Software Factories: Assembling Applications with Patterns, Models, Frameworks, and Tools_, Wiley, 2004 (book existence corroborated via search metadata for [Springer SPLC 2004 chapter](https://rd.springer.com/chapter/10.1007/978-3-540-28630-1_19) (off-list, 0.6, bibliographic only) and [Keith Short's MSDN blog](https://learn.microsoft.com/en-us/archive/blogs/keith_short/an-article-on-software-factories)). Revision 1: all quotes above were checked against the full article text returned by the fetch in this session.
**Confidence**: High for what Greenfield/Microsoft claimed (primary source fetched, quotes verbatim). This is one author's position, so it is a statement of intent, not evidence of results.
**Analysis**: The strongest intellectual ancestor of this repo's factory. "Encapsulate knowledge as reusable assets ... move from documentation to automation" maps almost one-to-one onto _skills_ (packaged procedural knowledge) and AGENTS.md (configured environment). What differs: 2004 factories encoded knowledge in DSLs, code generators and frameworks (deterministic, expensive to build, narrow); agent factories encode it in natural-language instructions consumed by a probabilistic model (cheap to write, broad, non-deterministic, so it needs verification gates).

#### F1.4 Recent "AI / agentic software factory" usage: issue queue -> agents -> verification -> human merge gate

**Evidence**: 2025-2026 vendor and practitioner material converges on a shape: work arrives from a queue/backlog (issues), specialized agents triage/spec/implement/review in isolated workspaces, verification runs automatically, and a human keeps an explicit merge gate. Examples: Warp docs describe specialized agents "for triage, spec, implementation, and review, producing pull requests for your team to merge"; Vercel describes turning GitHub/Linear work items into "reviewed draft pull requests" through agent stations. One practitioner reports their first factory "flooded the team with pull requests nobody asked for."
**Source**: Search-result summaries of [Vercel docs](https://vercel.com/docs/agent-resources/software-factory), [Warp docs](https://docs.warp.dev/platform/software-factory/), [Builder.io blog](https://www.builder.io/blog/build-an-agentic-software-factory-starting-with-one-bug). Platform-level support for the same flow: GitHub Copilot coding agent "can research a repository, plan changes, and implement them ... opens one pull request per task", with the caution "Logs do not replace your own review and testing" — [GitHub Docs: About Copilot coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent) (fetched).
**Confidence**: Medium. The usage pattern is consistent across sources, but the vendor sources are outside the trusted list (commercial interest, reputation ~0.6) and were seen only as search summaries; GitHub Docs is the one fetched official source.
**Analysis**: "Software factory" in 2025-26 is mostly a marketing term with no single owner or definition. The repo's own definition ("coding agents, instructions, skills, and workflows that turn issues into tested, reviewed code") matches this shape and is more modest.

### Area 2: Why encode practice as agent instructions, skills and workflows

#### F2.1 AGENTS.md: a README for agents, an open cross-tool convention

**Evidence** (fetched): AGENTS.md is "A simple, open format for guiding coding agents", "a README for agents". It sits apart from README because READMEs are for humans and agents need extra context: build steps, tests and conventions. There are no required fields. Typical content: project overview, build and test commands, code style, testing instructions, security. The nearest file in the directory tree wins, and explicit user prompts override everything. Supported by Codex, Jules, Gemini CLI, Cursor, GitHub Copilot coding agent, VS Code, Aider and others. "Now stewarded by the Agentic AI Foundation under the Linux Foundation."
**Source**: [agents.md](https://agents.md/) (fetched). Corroboration: GitHub Docs says "custom instructions let you save ... repository conventions" for the coding agent ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Anthropic says Claude Code loads CLAUDE.md "up front" ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).
**Confidence**: High (3 sources).
**Analysis**: The repo's AGENTS.md contains exactly the convention's recommended content: project description, build/test scripts, and pointers to docs/agents/\*. It does not use CLAUDE.md. Because AGENTS.md is a cross-vendor standard, the practice stays portable across agent tools, which supports goal 3 ("reuse on other projects").

#### F2.2 Skills: reusable, on-demand procedural knowledge with progressive disclosure

**Evidence** (fetched): "Skills are reusable, filesystem-based resources that give Claude domain-specific expertise: workflows, context, and best practices that turn a general-purpose agent into a specialist. Unlike prompts ... Skills load on demand." Benefits: "Specialize", "Reduce repetition: Create once, use automatically", "Compose capabilities". Progressive disclosure: metadata (~100 tokens) is always loaded, the SKILL.md body when triggered, and resources/scripts only as needed. Security: "Use Skills only from trusted sources ... a malicious Skill can direct Claude to call tools or run code in ways that don't match the Skill's stated purpose", "Treat like installing software."
**Source**: [Claude Docs: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) (fetched; docs.claude.com redirects here). Corroboration: [mattpocock/skills README](https://github.com/mattpocock/skills) (fetched): skills should be "small, easy to adapt, and composable. They work with any model"; existing process frameworks "take away your control and make bugs in the process hard to resolve."
**Confidence**: High for the definition (authoritative vendor doc). Medium-High for the rationale (2 independent sources).
**Analysis**: Skills are the agent-era version of Greenfield's "guidance packages": codified know-how that is loaded only when relevant. The repo has _no skills checked in yet_ (`.agents/skills/.gitkeep` only). Its docs/agents/*.md files are *configuration consumed by\* mattpocock skills (they map the skills' abstract vocabulary to this repo's tracker, labels and doc layout). That is an adapter layer, not skills of its own.

#### F2.3 Context engineering: why instructions should be small, clear and loaded just in time

**Evidence** (fetched): Context engineering is "the natural progression of prompt engineering ... the set of strategies for curating and maintaining the optimal set of tokens." "Context ... must be treated as a finite resource with diminishing marginal returns." It names "context rot" and an "attention budget". System prompts should be at "the right altitude", between brittle hardcoded logic and vague guidance. Claude Code uses a hybrid approach: CLAUDE.md is loaded up front, and other files are pulled just in time via glob/grep.
**Source**: [Anthropic Applied AI, "Effective context engineering for AI agents", 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Corroborated by the progressive-disclosure design in [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) and the nested-nearest-file design of [agents.md](https://agents.md/).
**Confidence**: High (3 sources, though 2 are from Anthropic; agents.md is independent).
**Analysis**: This explains the repo's _layering_: a short AGENTS.md (always loaded) points to docs/agents/*.md (read when a skill needs them), and domain.md says to read CONTEXT.md/ADRs *before exploring\* but to "proceed silently" if absent. The aim is a small always-on context with details pulled in on demand.

### Area 3: Triage labels, ready-for-agent vs ready-for-human, issue-driven flow

#### F3.1 The five state roles come from mattpocock/skills' triage state machine

**Evidence** (fetched, primary SKILL.md): state roles: `needs-triage` "maintainer needs to evaluate"; `needs-info` "waiting on reporter for more information"; `ready-for-agent` "fully specified, ready for an AFK agent"; `ready-for-human` "needs human implementation"; `wontfix` "will not be actioned". An unlabeled issue goes to needs-triage, and from there to one of the other four. needs-info returns to needs-triage on reply. Each triaged issue carries exactly one category role (`bug`/`enhancement`) and one state role. "The maintainer can override any transition."
**Source**: [mattpocock/skills triage SKILL.md (raw)](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/triage/SKILL.md) (fetched); [aihero.dev skills-triage](https://www.aihero.dev/skills-triage.md) (fetched; same author ecosystem, off-list, 0.6. **Not an independent cross-check**, used only for additional wording from the same author): ready-for-agent = "Fully specified, with an agent brief attached. An AFK agent can take it"; ready-for-human = "The same brief, plus why an agent can't do the work: judgment, external access, manual testing." The agent brief "is the contract", and the original report is only context. Briefs name types, signatures and behavioural contracts, not file paths, "because they can sit for weeks while the code changes."
**Confidence**: High for what the labels _mean upstream_ (primary SKILL.md is authoritative for its own definitions). Single author with no independent source, so the _rationale_ is Medium.
**Analysis**: The ready-for-agent / ready-for-human split is a **delegation decision made at triage time by a human**. Its criterion is not "easy vs hard" but "fully specifiable and verifiable without judgment, external access or manual testing." "AFK" (away from keyboard) means the agent runs unattended and the human comes back to review the result. The repo's [triage-labels.md](../agents/triage-labels.md) adopts the five _state_ roles but does not list the two _category_ roles (bug/enhancement). That gap may be deliberate or an omission; flag it in the Explanation.

#### F3.2 Why a human-owned delegation gate: autonomy compounds errors, so humans keep checkpoints

**Evidence**:

- Anthropic (fetched): "Agents can then pause for human feedback at checkpoints or when encountering blockers." Autonomy brings "higher costs, and the potential for compounding errors". "We recommend extensive testing in sandboxed environments, along with the appropriate guardrails." Advice: "find the simplest solution possible, and only increasing complexity when needed." — [Anthropic, "Building effective agents", 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents).
- Claude Code docs (fetched): the table's "Who has the last word" row is "Branch protection, a person who approves the merge" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- Kief Morris (fetched) separates the human-owned _why loop_ ("turning our ideas into working software and iterating as we learn") from the agent-runnable _how loop_, and humans _in_, _out of_, or _on_ the loop. "On the loop" means "change the harness that produced the artefact so it produces the results we want" — [Morris, "Humans and Agents in Software Engineering Loops", martinfowler.com, 2026-03-04](https://www.martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html).
- GitHub (fetched): "Logs do not replace your own review and testing" — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent).
  **Confidence**: High (4 sources from 3 independent organizations: Anthropic (2 documents), Thoughtworks/martinfowler.com, GitHub).
  **Analysis** (interpretation; design intent, not observed operation): The triage convention is _designed_ to put Morris's why/how split onto the issue tracker. A human triages (why loop: is this worth doing, is it specified?), an AFK agent would take `ready-for-agent` work (how loop), and `ready-for-human` names the residue that cannot be delegated. _If adopted on the tracker_, the labels would make the delegation decision explicit and reviewable rather than implicit in someone's head. **Current state**: the convention is documented in `docs/agents/triage-labels.md` only. Whether the labels exist on GitHub was not verified (gh unauthenticated / unavailable in this session), and nothing in the repo reads or applies them automatically. Under the convention, the issue is the unit of work and its brief is the contract.

#### F3.3 Issue-driven flow: GitHub Issues + gh as the factory's queue

**Evidence**: The repo's [docs/agents/issue-tracker.md](../agents/issue-tracker.md) makes GitHub Issues the system of record ("Issues and specs for this repo live as GitHub issues. Use the `gh` CLI for all operations"). It also defines a "wayfinder" map/child-ticket model with native issue dependencies for work too big for one session. Externally, GitHub's coding agent takes one task per PR ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Vendor "AI software factory" pipelines start from an issue/backlog queue (F1.4).
**Confidence**: Medium-High (local fact High; the general pattern rests on 1 official + vendor sources).
**Analysis**: Using the tracker as the queue keeps the factory tool-agnostic: any agent with `gh` can participate. It also gives a durable, reviewable record of decisions (comments, labels, briefs) outside any single agent's context window, which is context engineering at the team level.

### Area 4: Quality gates and TDD with agents

#### F4.1 Agents need an executable pass/fail check; otherwise the human becomes the test suite

**Evidence**:

- Claude Code docs (fetched): "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually _is_ done, 'looks done' is all it has to go on. In practice that makes you the test suite." The check can be "A test file / A build's exit code / A linter". "If your repo already has one of these, the single most useful line in your `CLAUDE.md` is the command that runs it." Also: ask for _evidence_, because "'All tests pass' on its own tells you very little." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
- Anthropic (fetched): "it's crucial for the agents to gain 'ground truth' from the environment at each step"; "Code solutions are verifiable through automated tests" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- Morris (fetched): agents, like developers who "write and run tests as we work", do better when they can assess their own code. The harness is "The collection of specifications, quality checks, and workflow guidance" — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html).
- mattpocock/skills: without feedback loops "the agent will be flying blind" — [github.com/mattpocock/skills](https://github.com/mattpocock/skills).
- Willison (fetched; paraphrase from the fetch summary, not a verbatim quote): agents work well with a robust test suite, and without one an agent may claim something works without having tested it — [Willison, "Vibe engineering", 2025-10-07](https://simonwillison.net/2025/Oct/7/vibe-engineering/).
  **Confidence**: High (5 sources, 4 independent: Anthropic (2 documents), Thoughtworks/martinfowler.com, Pocock, Willison).
  **Analysis**: This is the main reason `npm run checks` (format:fix -> lint:fix -> typecheck -> test) is listed in AGENTS.md. It is _meant_ to give the agent a single executable definition of "done". Caveat (local inference, H2): with no `src/` and no tests, the check currently has nothing to check and would most likely fail on tool defaults. It becomes a meaningful definition of done only once the first story's tests exist.

#### F4.2 Instructions are probabilistic; enforcement must be deterministic

**Evidence** (fetched): Claude Code docs classify every instruction as non-deterministic ("your prompt, `CLAUDE.md`, or a skill ... there's no _guarantee_ that it'll follow your instructions") or deterministic ("a hook, a deny rule, or a managed setting ... applies this every time"). For "When it's done": non-deterministic = "A request for evidence, `/goal`, `/code-review`"; deterministic = "Tests, typecheck, a `Stop` hook, CI". "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." "Keep the enforced set small." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices). Kent Beck reports agents "disabling or deleting tests" as a warning sign of the genie "cheating" — [Beck, "Augmented Coding: Beyond the Vibes", 2025-06-25](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes) (fetched).
**Confidence**: Medium-High (1 authoritative vendor doc + 1 practitioner primary source; consistent).
**Analysis** (important honesty point for the Explanation): In this repo, `npm run checks` is _named_ in AGENTS.md as "the pre-commit gate", but **nothing enforces it**. In the committed tree there is no git hook (no husky, `core.hooksPath` or lint-staged), no Claude hook and no CI workflow that runs tests/lint/typecheck. The only CI workflows are `actions-lock` (supply-chain pinning of workflow actions; its comment calls it a required check on main, unverified) and the Pages build. ADR-0001 also notes `npm run checks` does not cover the site. So today the gate is an _instruction_ (probabilistic), not _enforcement_ (deterministic). That is the gap between aspiration and reality.

#### F4.3 TDD is a stronger fit with agents, but agents may ignore it or cheat

**Evidence**:

- Beck (fetched, primary): "In augmented coding you care about the code, its complexity, the tests, & their coverage" vs vibe coding where "you don't care about the code." "You can see from the first commits that I was trying to get the genie to use TDD." Warning sign: "Any indication that the genie was cheating, for example by disabling or deleting tests." Unfinished: "I'm still working on getting the genie to care as much as I do about simplicity." A reader comment reports AI "simply ignored my instructions to use a TDD cycle." — [newsletter.kentbeck.com](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes).
- Beck called TDD a "superpower" with agents because agents introduce regressions (Pragmatic Engineer podcast, June 2025). Seen only via secondary summaries, so not independently verified.
- mattpocock `tdd` skill: "Red-green-refactor, building or fixing one vertical slice at a time" — [github.com/mattpocock/skills](https://github.com/mattpocock/skills).
- Claude Code docs: a reviewer "that hasn't seen how the code was written" (fresh subagent / `/code-review`) "isn't swayed by the reasoning that produced the code". Also: "A reviewer that's asked to find problems will always find _something_." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices).
  **Confidence**: Medium-High (2 independent primary sources plus vendor doc; the "superpower" quote is Low).
  **Analysis**: Project goal 1 ("test-first, one user story at a time") matches this. Tests written first are the agent's ground truth and the human's spec. The known failure mode (agent edits or deletes tests to go green) is the reason review must look at test diffs, and the reason a deterministic CI gate matters.

#### F4.4 Industry data: AI amplifies the existing system; instability rises without solid foundations

**Evidence**: "AI improves throughput, but often at the cost of stability if your foundation isn't solid", and the September 2025 report "confirmed the amplifier effects of adopting AI throughout the software lifecycle" — [Harvey, "DORA 2025: Year in review", dora.dev, 2026-01-07](https://dora.dev/insights/dora-2025-year-in-review/) (fetched). Search summaries of the report quote "AI's primary role in software development is that of an amplifier" and that AI adoption "is currently associated with increasing instability", with roughly 5,000 respondents — [Google Research listing](https://research.google/pubs/dora-2025-state-of-ai-assisted-software-development-report/), [InfoQ coverage](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025) (not fetched).
**Confidence**: Medium-High (authoritative research body; full report not read).
**Analysis**: This is the empirical argument for building the gates _before_ scaling agent throughput. A factory without quality control amplifies defects. That echoes the Japanese factories' emphasis on quality control (F1.2).

#### F4.5 Tests are the professional baseline for working with agents

**Evidence**: Willison defines "vibe engineering" as "seasoned professionals accelerate their work with LLMs while staying proudly and confidently accountable for the software they produce". He lists practices that make agents effective (paraphrased from the fetch summary): automated testing, planning in advance, documentation, version control, CI/automated formatting and linting, a code review culture, and manual QA. He also argues "AI tools amplify existing expertise" — [Willison, "Vibe engineering", 2025-10-07](https://simonwillison.net/2025/Oct/7/vibe-engineering/) (fetched). Fowler: agentic engineering is "concerned with the code, often giving it detailed review", and "Humans are still responsible for what the software does and how it works" — [Fowler, "Agentic Engineering", bliki, 2026-05-21](https://martinfowler.com/bliki/AgenticEngineering.html) (fetched).
**Confidence**: High (Willison, Fowler, Beck, Anthropic, DORA are independent and agree on direction).
**Analysis**: The repo's AGENTS.md + `npm run checks` + Prettier/ESLint/tsc/Vitest toolchain is a minimal version of Willison's list. Missing pieces: CI for code checks, preview environments (n/a), and a recorded review practice.

### Area 5: Why Diataxis for documenting the practice; why a kata as the testbed

#### F5.1 Diataxis separates four user needs. Explanation is the "why" quadrant

**Evidence** (fetched): "Diátaxis identifies four distinct needs, and four corresponding forms of documentation": tutorials, how-to guides, reference, explanation. Compass: explanation is content that "informs cognition" and serves "acquisition of skill". "Explanation is a discursive treatment of a subject, that permits _reflection_." It should make connections, provide context ("design decisions, history, and technical constraints"), "talk about the subject", "admit opinion and perspective" ("Explanation can and must consider alternatives"), and stay closely bounded. It must avoid instruction and reference. Adopters quoted on the site include Cloudflare ("Diátaxis became our north star for information architecture"), Gatsby and Vonage.
**Source**: [diataxis.fr](https://diataxis.fr/), [diataxis.fr/explanation](https://diataxis.fr/explanation/), [diataxis.fr/compass](https://diataxis.fr/compass/) (all fetched; same origin).
**Confidence**: High for what Diataxis prescribes (authoritative primary). Medium for "why it suits this repo" (interpretation; independent adoption evidence comes only from testimonials on the same site).
**Analysis**: Diataxis suits a _practice_ being documented for reuse (goal 3). Newcomers need a tutorial, practitioners need how-tos (e.g., "triage an issue for an agent"), agents and humans both need reference (label tables, commands), and adopters need explanation (why a factory, why these gates). Bonus (interpretation): agent-facing files (AGENTS.md, docs/agents/*.md) are essentially *reference\* documents, so Diataxis also clarifies which docs are written for agents and which for humans. Per ADR-0001, the site uses Jekyll/just-the-docs with "Diataxis sections driven by front matter" so it can be reused across projects.
**Guidance for the Explanation writer** (from Diataxis): include history (F1), alternatives and counter-arguments (Trade-offs section), and analogies ("an X in system Y is analogous to a W in system Z. However..."). Do not include commands or step lists.

#### F5.2 A kata is a bounded, low-stakes, incremental testbed

**Evidence**:

- Trusted (fetched, 2003): "Dave Thomas, one of the book's authors [*The Pragmatic Programmer*], has an excellent weblog on which he has been posting a series of programming exercises called Kata". "Each one provides an interesting thought exercise with no instantly obvious solution." — [Willison, "Code Kata", simonwillison.net, 2003-08-27](https://simonwillison.net/2003/Aug/27/codeKata/). This traces the _Dave Thomas / Kata_ link to a trusted source. It does not establish that Thomas _coined_ the term; say "popularized by" or "associated with".
- Off-list, non-load-bearing (0.6): an InfoQ 2007 note on coding dojos ("meeting places where developers can go to practice coding together") frames katas as deliberate practice and reports Emily Bache recommending them for improving at TDD — [InfoQ, Elssamadisy, 2007-09-01](https://infoq.com/news/2007/09/coding_dojos) (fetched via summary, so wording not re-verified).
- Off-list, non-load-bearing (0.6, search summary only): RPG Combat kata attributed to Daniel Ojeda (slide deck; first run at SoCraTes Canaries 2016), structured "by iterations" — [Ojeda's SlideShare deck](https://www.slideshare.net/DanielOjedaLoisel/rpg-combat-kata) (not fetched).
  **Local evidence**: [user-stories.md](../../user-stories.md) has five sections (Damage and Health, Levels, Factions, Magical objects, Changing level). [site/index.md](../../site/index.md) says the rules "are delivered as incremental user stories, each one adding constraints that push the design forward." AGENTS.md says "six user stories", while user-stories.md has five `##` sections and 14 numbered rules. The doc writer should resolve this discrepancy. [README.md](../../README.md) calls the repo a "starting template", so the kata scaffold itself came from a reusable template.
  **Confidence**: Low-Medium. The Thomas/kata link has 1 trusted source. The deliberate-practice framing and the RPG kata origin rest on off-list sources and are non-load-bearing. The rest is local fact.
  **Analysis** (interpretation): A kata isolates the _factory_ variable. The domain is small, well known and fully specified, so failures can be attributed to the process (instructions, skills, gates) rather than to domain ambiguity. Each incremental story is a natural _issue-sized_ unit for the triage -> agent -> review loop, and later stories (Levels, Factions, Magical objects) force refactoring, which tests whether agent-written code stays maintainable. The limit is that a kata lacks real-world properties (legacy code, ambiguous stakeholders, production ops), so results do not generalize automatically.

## Conflicting Information

### C1: Bemer and the 1968 NATO conference

**Position A** (unsourced; a common association, not cited): the term "software factory" is sometimes linked to the 1968 NATO Software Engineering Conference. **Position B** (F1.1, source [7], snippet-level, Medium-Low): Cusumano's history places Bemer's proposal in a 1968 paper written at GE. **Assessment**: Neither position is established by a fetched trusted source. Position B has at least a named source. The Explanation should use F1.1's hedge ("according to Cusumano's history, Bemer at GE is credited with an early software-factory proposal around 1968") and should not connect it to the NATO conference. (Revision 2: the claims about "published 1969", McIlroy's NATO talk, Bemer's 1966 checklist, the core.ac.uk copy and the podcast were deleted. They were not in the source table and are not needed.)

### C2: Does the factory metaphor fit?

**Position A** (Greenfield 2004): industrialization patterns _can_ apply to development, through economies of scope. **Position B** (critics: Davidson/Cook 2006, Cockburn as attributed, Bosch): software is design/knowledge work, and the craftsman remains. **Assessment**: Not truly contradictory. Greenfield also rejects "drones" and agrees developers stay central. Both positions converge on "the factory automates the _tools and rote work_, not the design". Present this as a tension to manage, not a winner.

### C3: Human in the loop vs on the loop

**Position A** (Claude Code docs, GitHub Docs, Fowler 2026): humans review and approve merges, so they are the last word. **Position B** (Morris 2026): humans as inner-loop gatekeepers become the bottleneck and should move "on the loop", improving the harness. **Assessment**: Complementary. The repo does both: humans triage and review (in the loop) and maintain instructions/skills (on the loop).

### C4: Upstream naming drift

The repo's `domain.md` uses `CONTEXT.md`, while the current mattpocock/skills README mentions `GLOSSARY.md`. Likely an upstream rename after this repo's setup. Unverified.
